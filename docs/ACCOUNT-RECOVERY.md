# 账号恢复与验收

## 已修复的无限等待

2026-10-06，正式账号状态长时间停在 `connecting / started`。运行中线程栈定位于
`DrissionHandler.get_cookies → Listener.steps`：`count=10` 仅限制收到的包数，未设置等待超时；没有新包时不会返回。

- 网络包监听改为每次最多等待2秒、最多10个包；无新包后继续读取已有结果并关闭浏览器。
- 同步与异步恢复统一遵守主引擎的暂停判断。`preflight_deferred`、`hard_block` 或已识别的验证硬失败不再启动备用引擎重复尝试。
- 保留原有失败退避、人工验证与正常恢复路径；不把页面跳转或Cookie存在当成登录成功。

回归：`tests/test_recovery_regressions.py`。使用真实DrissionPage监听器和空队列复现等待，无平台请求。
全量78个测试通过。账号在线必须另验真实Token、认证连接与心跳；测试通过不代表平台验证通过。

## 日常排查

后台账号的“刷新状态”读取实时状态，而不是只看容器health。
- `started` 长时间不变：查任务和线程是否卡住，避免反复点登录。
- `password_login_backoff_wait`：失败后冷却中，查看具体原因。
- 需要本人扫码/验证：使用后台对应登录入口，确认后重新查询四项链路。
- 消息流就绪、真实收发、长时间保活分别验收。

敏感Cookie、密码、验证链接和截图只留私有运行目录，禁止提交到Git。

## 恢复状态显示

`password_login_backoff_wait` 保留上游接口状态码，提示按实际原因区分滑块失败、人工验证、账密错误、平台风控、浏览器异常，避免把每种失败都写成密码错误。
诊断面板优先显示“恢复冷却中”或“等待人工验证”，不再被“重连中”覆盖；普通连接与真正就绪状态保持原样。
验证：83个Python测试、4个前端逻辑测试通过。2026-10-06首次修复发布后，真实流程约37秒结束并进入600秒冷却，Token/认证连接尚未就绪；不是账号上线验收。

## 同账号Token互斥

兼容原版0764f11：同账号多实例/多线程/多进程的Token刷新共用文件锁，存于DB_PATH同级的`token_locks`（单机Linux Docker共享数据目录）。实例内去重仍保留。持锁贯穿恢复；崩溃由内核释放，等待超时不放行并发请求，不引入Redis。多机部署需另接分布式锁。
测试覆盖双实例竞争、等待超时、取消释放、进程退出释放及不同账号互不阻塞。
