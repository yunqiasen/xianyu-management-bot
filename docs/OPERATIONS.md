# 增强版使用与维护

## 范围

源码为一份仓库：`main`同步原版，`xianyu-management-bot-fork`承载增强功能。切分支、测试或构建都不等于发布。现用旧系统与增强版数据分开；正式切换、提交、推送和部署分别确认。

## 账号出现问题时

1. 账号页打开“运行状态”：分别看业务状态、连接状态、失败原因、最近成功和下次重试；页面打开不表示账号可用。
2. 要换Cookie用扫码刷新或凭据更新。密码不是扫码必填项；只在需要账密恢复时使用。空白编辑保留已保存秘密，明确清除按钮才清空。
3. 代理故障先修绑定，限流按下次时间等待，网络断线先重连；凭据确实失效才尝试账密恢复。两次失败后保留暂停，不循环扫码或重登。
4. 需要人工验证时在同一账号验证页操作；支持点击、输入和拖动。取消/超时关闭相应浏览器资源，完成后仍先检查会话。短信、人脸由账号持有人完成。
5. 手动停用持续有效；刷新成功或程序重启不顺带打开自动业务。删除账号前先看关联影响，别用删除修复登录。

## 固定代理与订阅节点

账号编辑的代理项填写协议、主机、端口及可选认证。HTTP、消息连接与登录浏览器使用同一绑定；已有绑定失效时停下，不切到别的出口。

```text
订阅 → 独立代理客户端 → 固定节点的监听端口 → 账号明确绑定
```

- 后台不接订阅链接，也不复用已弃用的`xianyu-proxies`编排。
- 本地服务连接宿主机可用的固定端口；Docker中的`127.0.0.1`指容器自己。宿主机端口需使用实际可达地址，Linux部署可显式配置`host.docker.internal:host-gateway`，并限制监听/访问范围。
- 一个端口对应固定节点，订阅更新不要悄悄换节点。变更代理后在配置面板应用到消息/调度服务，检查缺失消费者及失败原因。
- “共享业务频率”填实际需要的低频值；例如最小5秒、每分钟6次只是配置示例，不是平台承诺。没有明确配置或配置非法时业务停止并提示，不臆造无限预算。

## 回复和AI

先决定回复策略，再配模型：

| 策略 | 顺序 |
|---|---|
| 迁移账号`legacy` | 商品专属 → 商品关键词 → 通用关键词 → 商品/账号默认 → AI |
| 新账号`ai_first` | 商品专属 → 商品关键词 → 通用关键词 → AI → 商品/账号默认 |

启用的空回复、只回一次已用完、人工暂停及明确跳过会结束回复链。**默认模板挡住AI时，API再通也不会调用模型。** 商品专属与商品默认是两个设置。

AI面板选择正确协议、填根地址或完整接口地址、模型/部署/应用ID、密钥，先保存再测试。测试与实际消息共用调用链；日志会显示规则跳过、请求错误或正文来源。默认请求超时60秒，出错不自动重复付费生成。预设应用后复制给账号，删预设不影响副本。

人工消息和机器人共用历史；人工回复按账号/会话暂停。高级过滤支持买家/系统/AI出站，默认仅本账号；“全部账号”覆盖同一后台用户现有及未来账号。暂停可独立填分钟，0也有效。全局/用户/账号默认值面板会显示最终来源；只有选择继承的字段才随上层改变。

可直接参考的普通模板：

| 用途 | 示例 |
|---|---|
| 库存咨询关键词“还在吗” | 在的，商品详情和成色都在页面里。想确认哪一项可以直接说。 |
| 发货时间 | 付款后按商品页约定时间处理；有特殊时间要求请先沟通。 |
| 人工接管 | 这个问题需要核实，稍后给你准确答复。 |

“求小红花”是按订单向买家请求评价，不是保活；与自动评价、擦亮分开开关。迁移不额外打开这些功能。

## 商品、订单与卡密

- 素材编辑先校验类目、图片和完整规格组合；发布后快照保留，后改素材不篡改历史。
- 批量发布逐件看状态；明确失败项可重试，unknown先核对平台商品身份。取消只停止尚未执行项。
- 多SKU订单逐明细匹配卡券，数量含购买数及规则发放倍数；整单预占失败则回滚整单预占。
- 内容确认与平台发货确认分开。卡已发送而确认失败时点“仅补确认”，不是“真正补发”。供应商已受理但回执丢失先查结果，不再次购买。
- 真正补发要新请求身份、原因和明确确认；旧履约记录保留。退款/关闭、规则变化和执行权失效会阻止旧任务继续出站。
- 擦亮可设账号时区、跨午夜窗口和随机时间；计划先持久保存，重启不重抽、不集中补跑错过周期。

## 通知与日志

先配置渠道并测试，再给账号绑定和选择事件。支持QQ OneBot、钉钉、飞书、企业微信、Bark、Telegram、PushPlus、Webhook和邮件；渠道受理不等于对方阅读。仅明确未受理按60/300/900秒最多再试三次；unknown保留核实状态。

日志页按服务/账号/关联ID查同一次操作，导出先脱敏。新配置运行文件在线30天；旧显式保留天数继续沿用，更早文件归档而非删除。结构化运行日志清理只移动30天前明确终态，unknown/处理中保留。操作审计由备份调度维护，180天前已完成的管理动作进入独立归档，原操作者、来源ID及时间仍可查；未知动作及在途引用继续在线。

## 备份与恢复

1. 在调度任务中触发数据库备份，检查对应日志成功后下载SQL.gz。仅文件存在不算恢复成功。
2. 后端`ADMIN_RESTORE_DATABASE_URL`指向**另一MySQL实例**的`xymb_restore_`前缀空库；后台点击“隔离库恢复验证”。同实例别名会被server_uuid检查拦下。
3. 校验文件SHA256、表/行数、外键及业务关联。恢复包含日志、防重事实、二进制/NUL、微秒时间和合法零主键；导出固定UTC及一致性只读快照，非InnoDB表报失败。恢复后连接设置还原。
4. 验证成功的切换前备份点击“设为保护点”。日7份、周4份、最近恢复点和保护点分别保留；最新备份没有匹配SHA256的真实恢复证据时不淘汰旧文件。
5. 恢复测试库用完后保持独立。下一次恢复需另一个空库或由运维明确清理该测试库；后台不自行清库。恢复演练不会覆盖当前业务库。

白名单数据管理只对通知配置开放关联删除；先预览、输入DELETE确认，并要求实际恢复过且匹配当前配置的备份。其他业务表仅脱敏只读。

## P5增强

- `XYMB_ENABLE_BARGAINING_V2=true`：按真实买家议价事件计数，保留最新完整往来；“评价”、刀具咨询等不计议价。
- `XYMB_ENABLE_MONITOR_V2=true`：监控完整基线、页码/代次校验、重启续页、价格修订及独立通知阶段。

两个开关默认false，三服务使用一致部署配置。新监控任务默认停用、5分钟/1页；首次完整基线不通知存量。旧任务带独立代理/自动下单/私信冲突时保持待处理，不隐式改成另一套自动行为。

## 运行与验证

原版三服务默认端口：Web 8089、消息8090、调度8091（最终以配置为准）。隔离依赖编排只绑定本机19006/19007/19379，独立卷且不挂旧数据。消息、调度及采集自动业务默认关闭；测试的真实三服务由验证器用随机端口启动并自行清理。

在仓库根目录运行：

```bash
.venv/bin/python tools/verification/run.py --plan
.venv/bin/python tools/verification/run.py \
  --integration-env "$PRIVATE_INTEGRATION_ENV" --output "$NEW_EVIDENCE_DIRECTORY"
```

环境文件应权限0600并指向`xymb-integration`依赖。验证器逐领域独立进程，包含非标准命名suite、前端检查/构建、Chromium、真实MySQL/Redis和第二MySQL恢复；零测试、跳过、超时或源码中途变化都会失败。测试日志和截图放源码仓库外。

迁移命令、增量回退及旧执行方停写边界见 [迁移说明](implementation/migration.md)。从干净提交构建候选镜像、单账号交接、真实业务和至少48小时观察见 [发布门禁](RELEASE.md)；增强代码的本地回归不代替这些记录。
