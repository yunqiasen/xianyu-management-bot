# 订单、卡密与履约

对应 DEV-26–30。发送内容与平台发货确认分别保存，不以HTTP接收任务代表已发货。

## 持久链

`订单事件/人工入口 → OrderDeliveryRuntime → DeliveryIntent → 库存预占/内容准备 → 发送确认 → 平台确认`。

- MySQL唯一业务身份与行锁裁决重复付款和库存竞争；多SKU按line_id分明细，整单全部明细预占成功才推进；任一不足整体回滚，不先发送部分卡。
- 卡券支持text/data/api/image；按订单SKU、购买数量和归属核对。缺SKU阻止通用卡错误兜底，多个匹配保持待处理。
- 内容逐件阶段持久记录。结果unknown保留预占，不重复发送；明确未发送才释放，已发送库存不因租期清理回池。
- API卡保存供应商请求身份与配置快照。已受理丢回执先查询或提交人工证据；不重复采购。图片卡检查所属用户与实际媒体路径。
- 先发送、先确认、仅卡密分别表达两个完成维度。内容已确认后的补确认沿用原意图，不取卡、不发送内容、不重复成功的免运费等确认子步骤。
- 平台确认首次之外最多三次明确失败重试，60/300/900秒；unknown先核对。耗尽保留待办。
- 真正补发需要独立请求身份、明确确认与原因；旧意图和操作者保留。退款、买家/会话变化、失权和旧版本阻止旧外发/写回。

## 接线

自动发货、原内部发货入口、后台人工发货及调度补发先检查已有持久意图。原对接/表单等专门能力保留原入口，但已有未知意图会阻止旁路重复给货。定时任务将“任务已接收”和“订单已发货”分别处理。

订单历史使用可查询任务、页检查点、取消/继续。原订单读取通过账号执行方，返回后的写入按owner/account/order限定，退款/关闭不被迟到付款回退；证据矛盾单列待核实。

## 页面与验证

`Orders → CommercePanel / DeliveryRulesPanel` 提供历史同步、规范化明细、意图查询、规则增改及预览、仅补确认、供应商查询/证据及真正补发。规则保存校验卡券/账号归属、数量和版本，新规则默认关闭。内容明细接口只向所属后台用户返回秘密内容，列表与普通日志脱敏。切换账号隔离整个面板实例；迟到的列表、内容与规则查询不回填新账号，离开的历史循环不继续翻页；同一面板的列表刷新按最新请求采纳。

`tests/commerce/`、四个 `ws_*.py`、`tests/integration/` 覆盖真实MySQL抢库存、重复事件、分件unknown、采购中断、确认中断及旧入口。`test_process_recovery.py` 另用真实MySQL、HTTP和独立进程，在采购/发送/确认的请求前、受理后未响应、响应后未落库，以及预占落库/确认失败落库处共11个位置SIGKILL；重启后先核实，发送/库存/采购不重复。

`tests/commerce/browser_flow.py` 在真实HTTP/数据库上延迟账号A的列表和内容响应，切换到账号B后释放响应，核实页面仍只展示B且旧内容保持隐藏。

原生旧标题规则保留双向SQLite LIKE语义（%/_、ASCII大小写及零分有效匹配），发放倍数按实际旧配置映射。源数据缺少逐件发送证据或身份冲突时保留待核实并停用；详见迁移说明。真实订单、供应商与平台确认另行验收。
